# Languages and translations

Translation outcome depends on three layers. Explain them whenever the user mentions languages.

1. **Site languages** (app, per site): the languages a site serves. A page language not enabled on the
   site cannot exist there (`language_not_enabled`).
2. **Organization translations setting** (app, org-wide): the gate for machine translation. When it is
   off, nothing is machine-translated, whatever passes request; validate warns `translations_disabled`.
3. **Pass `options.languages`** (manifest): the languages a pass requests for the pages it writes.

Effective languages for a pass = pass languages that are enabled on the target site, and only if the
organization gate is on.

Verbatim translations are different: files named `guide.fr.md` / `guide.pt-BR.mdx`, or with front matter
`lang: fr`, are imported as human translations of their source page directly (no machine translation),
but the language still has to be enabled on the site.

## Reading the outcome

```bash
gravity validate --json | jq '.data.i18n[] | {pass, languages, effective, reason}'
gravity show --json | jq '.data.passes[] | {name, languages, effectiveLanguages, i18n}'
```

`reason` says why `effective` differs from `languages` (site lacks the language, org gate off).

## Fixes

- `language_not_enabled`: enable the language on the site in the app, or remove it from the pass /
  delete the translation file.
- `translations_disabled`: an admin turns on translations in the organization settings, or remove
  `languages` from the pass to stop requesting them.
- A translation file without a matching source file is skipped with a warning naming the missing source.
